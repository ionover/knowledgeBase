# Репликация и отказоустойчивость

## Вопрос

- Что такое `leader`- и `follower`-партиции, ISR (`in-sync replicas`)?
- Как Kafka обеспечивает отказоустойчивость при падении брокера?

## Ответ

Как правило, количество реплик — 3: 1 основная, она же лидер, и остальные — фолловеры, которые понемногу синхронизируют
свои данные с лидером.

Как только лидер по какой-то причине выходит из строя, один из фолловеров становится лидером. Если все фолловеры и
лидеры кончились, то партиция блокируется, и из неё нельзя читать.

Есть реплики ISR, которые постоянно синхронизируются. Если реплика по каким-то причинам перестала синхронизироваться и
отстала от лидера, она не входит в перечень ISR. Её всё равно можно будет использовать, но тогда будет потеря сообщений,
которые не успели синхронизироваться. При этом если включён режим `all`, то должно быть достаточно ISR в пуле.

Для определения того, жив ли лидер, используется KRaft или ZooKeeper. Контроллер ждёт сердцебиения лидера.
Для определения того, рабочие ли фолловеры, используются `fetch requests`, и лидер считает фолловеров живыми,
если они укладываются в тайм-аут.

Отказоустойчивость обеспечивается наличием ещё 1 брокера-контроллера, который следит за тем, активен ли лидер, есть ли
готовые реплики, и он же назначает кого-то из фолловеров репликой.

По сути, Kafka — это набор модулей, и за счёт их количества и возможности «подстраховать» друг друга появляется
отказоустойчивость.
