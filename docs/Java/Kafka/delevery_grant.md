# Вопрос

Гарантии доставки.

Какие есть семантики доставки сообщений: `at-most-once`, `at-least-once`, `exactly-once`?

Как достигается `exactly-once` в Kafka (идемпотентный producer, транзакции)?

# Ответ

## At-most-once (не более одного раза)

Продюсер закидывает сообщения в Kafka и не ждёт. Можно потерять сообщение. Такая же проблема со стороны консьюмера
если он сдвинул офсет но не обработал сообщение то она потеряно, а если прочитал, но не сдвинул то это дубль.

## At-least-once (как минимум один раз)

Продюсер закидывает сообщение, брокер отправляет подтверждение (либо от лидера либо от лидер+реплики) и возвращает
подтверждение продюсеру. Возможны дубли.

## Exactly-once (только единожды)

Самый медленный вариант. По сути, он физически недостижим без выстроенное системы и общением между всеми членами
системы.

Чтобы включить его, в настройках продюсера указывается `enable.idempotence=true`, и тогда продюсер не будет дублировать
сообщения — это идемпотентность. Каждое сообщение начинает хранить в себе номер и статус, за счёт этого можно
дёшево выполнить дедупликацию. Продюсер ведёт sequence number, но это не спасает при смерти продюсера поэтому ещё
ведётся transactional.id.

Также используется транзакционное API, которое гарантирует, что доставлен пакет сообщений или ничего. У потребителя в
случае транзакции тоже есть возможность либо использовать `read_committed`, либо, как по умолчанию, читать всё. Для
этого потребителю нужно настроить isolation level. producer.sendOffsetsToTransaction() — способ атомарно закоммитить
offset потребления вместе с записью результата обработки в рамках одной транзакции.

Важно, что отсутствие дублирования на полном цикле «отправка — запись — чтение» может гарантироваться только совместной
настройкой всех элементов системы: продюсер должен не отправлять дубли, консьюмер должен явно читать доставленные батчи
и сообщать о том месте, где он читает.
