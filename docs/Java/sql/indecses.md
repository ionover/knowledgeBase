# B-tree

Обеспечивают возможность быстрого поиска по таблицам за счёт организации поиска в виде дерева, и, соответственно, поиск
уменьшается с O(n) до log(n).

B-tree — буквально бинарное дерево.

Индексная структура — это отдельный файл данных. По сути, это таблица, написанная таким образом, чтобы можно было
успешно совершать поиск по нужной таблице. То есть таблица бьётся на страницы, страницы нумеруются и так далее.

В индексах может храниться информация из таблицы, так что при некоторых запросах смотреть в таблицу даже не нужно.

- `CREATE INDEX idx_user ON test.user (id);` — просто создать индекс.

- `CREATE INDEX idx_user ON test.user (id) TABLESPACE ssd;` — создать индекс в конкретном пространстве (например, на
  конкретном диске).

- `CREATE UNIQUE INDEX idx_user ON test.user USING BTREE (id);` — создаёт индекс и заставляет значения быть уникальными.

- `CREATE INDEX IF NOT EXISTS idx_user ON test.user (id, name);` — `IF NOT EXISTS` не даст создать такой же по имени.

- `CREATE INDEX idx_user ON test.user (name DESC NULLS FIRST);` — из-за бинарного дерева индексы все отсортированы,
  можно влиять на сортировку.

- `CREATE INDEX CONCURRENTLY idx_user ON test.user (id, name);` — обычно для создания индекса таблица блокируется
  полностью (кроме Select). Если мы в рантайме, то можно использовать `CONCURRENTLY`: процесс будет дольше, зато можно
  записывать
  в таблицу.

- `DROP INDEX CONCURRENTLY test.idx_user;` — удалит индекс.

- `REINDEX (VERBOSE) { INDEX | TABLE | SCHEMA | DATABASE | SYSTEM } name` — запустить процедуру пересоздания индексов.

## Дополнительно

- `CREATE INDEX idx_user ON test.user (UPPER(name));` — индекс на функцию.

- `CREATE UNIQUE INDEX idx_user ON test.user (name) WHERE id BETWEEN 0 AND 100;` — индекс на часть таблицы.

- `CREATE INDEX idx_user ON test.user (id) INCLUDE (name);` — индекс с включением. Такой индекс хранит `name` только в
  листьях.

Кроме B-tree существуют GIN, GiST, HASH, BRIN индексы

## Применяемость индексов

SQL сам решает, может ли он применить индекс при поиске. Например, если у нас `index` по `id`, а мы пишем
`where name like 'God'`, то оптимизации от индекса никакой не будет. Важно это учитывать при индексах на функцию или
часть таблицы.

### Семейства операторов

Разные семейства операторов предполагают разные улучшения для разных структур данных. Например, для строки есть
`text_ops`, который хорошо будет работать с запросами `=`, `>` и `<`.

При этом оператор `text_pattern_ops` уже может работать с `LIKE`.

## Составные

Нельзя создать универсальный индекс, который одинаково быстро будет работать для всех задач. Если сделать его
универсальным, то это не даст максимального прироста скорости.

Если есть таблица с именами людей и датами регистрации и мы постоянно ищем по именам, то нам подойдёт составной индекс:

```sql
CREATE INDEX idx_user ON test.user (name, date);
```
(Такой индекс хорошо подходит и для обычного where name)

Но если постоянно ищем по датам, то дерево по именам может оказаться неоптимальным, и тогда лучше создать:

```sql
CREATE INDEX idx_user ON test.user (date, name);
```


Особых правил нет, и нужно под каждую базу и бизнес строить свои индексы. Важно понимать, что они занимают место и CPU.

Рекомендуют добавлять в порядке `WHERE`:

1. Равенство.
2. Сортировка.
3. Диапазон (`<>`).
